# 2. Critical existing safety invariant

Preserve this invariant exactly:

> If `app_confirmed_lsn = X`, then X must be the LSN of a COMMIT (`C`) row, and the corresponding transaction and all prior transactions represented by that watermark must have been durably applied to Delta.

The implementation must continue to enforce:

```text
selected watermark LSN == COMMIT row LSN
```

Do NOT revert to:

```python
new_watermark = raw_rows[-1]
```

unless the code has already proven that the final row is a COMMIT row.

The normal CDC processing model remains:

```text
PEEK
  ↓
decode
  ↓
group/fold complete transactions
  ↓
APPLY to Delta
  ↓
identify last successful COMMIT LSN
  ↓
persist checkpoint/state
  ↓
ADVANCE/GET changes only after successful persistence
```

Do not weaken this invariant while implementing Phase 3.

# 3. Phase 3 problem statement

The current fallback for a WAL gap is effectively:

```text
app_confirmed_lsn < restart_lsn
        ↓
WAL_GAP_DETECTED
        ↓
RECOVERY_REQUIRED
        ↓
full reload all active tables
```

This is safe but potentially very expensive.

We want to investigate and implement a more selective recovery mechanism:

```text
WAL pressure / impending WAL loss
        ↓
inspect unconsumed WAL using PEEK
        ↓
identify tables affected since the application's last safe point
        ↓
establish a safe recovery boundary
        ↓
selectively reload only affected tables
        ↓
create/use new CDC generation
        ↓
resume CDC
        ↓
verify
        ↓
retire old slot
```

Example:

```text
Active tables:
A B C D E F

WAL backlog contains changes to:

A
C
F

Recovery should ideally perform:

FULL LOAD:
A
C
F

No full reload:
B
D
E
```

# 4. Important architectural principle

Do NOT implement a PostgreSQL scheduled job simply to maintain a table-level LSN.

PostgreSQL does not natively maintain an authoritative:

```text
table → latest committed WAL LSN
```

mapping.

Instead, leverage the information already present in the logical decoding stream.

The recovery analyzer should inspect the old slot using a non-consuming operation such as:

```sql
pg_logical_slot_peek_changes(...)
```

with the existing wal2json configuration.

The objective is to derive:

```text
affected_table_set
```

from the unconsumed logical decoding stream.

The old slot must NOT be advanced merely to discover affected tables.

# 5. WP2 — Independent Recovery Source

Implement an independent recovery-analysis component.

Its responsibility is:

```text
old replication slot
        ↓
PEEK logical changes
        ↓
parse wal2json
        ↓
transaction-aware analysis
        ↓
affected tables
        ↓
recovery boundary / metadata
        ↓
durable recovery manifest
```

This component must be logically independent from the normal Delta-processing state.

It must not simply say:

```text
table is affected because table_latest_seen_lsn says so
```

The source of truth for determining affected tables during this recovery analysis should be the logical decoding/WAL stream itself.

The persisted recovery manifest should contain enough information to audit exactly how the affected-table set was determined.

At minimum capture concepts equivalent to:

```text
recovery_id
old_slot_name
old_slot_generation
scan_start_lsn
scan_end_lsn / analysis_boundary
affected_table
highest_observed_commit_lsn_for_table
recovery_status
created_at
updated_at
```

Adapt names to the existing project conventions.

# 6. Transaction-aware WAL scanning

The recovery analyzer must understand transaction boundaries.

For example:

```text
BEGIN
UPDATE table_A
UPDATE table_B
UPDATE table_A
COMMIT
```

must result in:

```text
affected tables:
A
B
```

and the transaction's COMMIT LSN must be associated with both affected tables.

Do not incorrectly treat individual row/change LSNs as the transaction watermark.

Handle:

* INSERT
* UPDATE
* DELETE
* multiple changes to the same table
* multiple tables in one transaction
* multiple transactions
* repeated changes to the same table
* transactions containing many changes
* empty ranges
* commit ordering
* wal2json BEGIN/COMMIT records
* schema-qualified table names
* quoted identifiers where applicable

Deduplicate the affected-table set.

# 7. Recovery scan must not consume WAL

The analysis operation must use a peek/non-consuming mechanism.

The following must remain true:

```text
Before analysis:
confirmed_flush_lsn = X

After analysis:
confirmed_flush_lsn = X
```

unless a completely separate, explicitly documented operation intentionally advances the slot.

Add a test proving that affected-table analysis does not advance the slot.

# 8. Recovery boundary — MOST IMPORTANT PART

Do not implement selective recovery until you have carefully designed and documented the recovery boundary.

The biggest correctness risk is:

```text
identify affected tables
        ↓
full load table
        ↓
new PostgreSQL changes happen
        ↓
new CDC starts
```

which can result in:

* lost changes
* duplicate changes
* stale full-load state
* inconsistent table state

You must establish a precise ordering between:

1. old-slot WAL analysis
2. new CDC generation / slot
3. snapshot/full-load
4. CDC resume

The design must guarantee that changes cannot silently fall between the full-load boundary and the new CDC boundary.

# 10. Snapshot consistency requirement

Selective full loads must have a defined consistency relationship with the new CDC boundary.

The implementation must answer:

> At what exact PostgreSQL state is the full-loaded table represented?

and:

> From what exact LSN does the new CDC generation capture changes?

The desired conceptual relationship is:

```text
PostgreSQL state at recovery boundary
             │
             ├── full-load affected tables
             │
             └── CDC captures changes after boundary
```

No change should be lost between those two mechanisms.

Document the exact mechanism used to guarantee this.

# 13. Selective full-load semantics

Only affected tables should be full-loaded.

Example:

```text

Reload:
A C F

Do not reload:

```

However, the implementation must have a safe fallback:

```text

corrupt,
or cannot establish a safe boundary,

```

Correctness is more important than reducing reload volume.

# 17. Important distinction: latest_seen_lsn vs last_processed_lsn

If table-level state already exists or is introduced, preserve this semantic distinction:

```text
latest_seen_lsn
```

means:

> highest relevant transaction commit LSN observed by the CDC/recovery reader for that table.

Whereas:

```text
last_processed_lsn
```

means:

> highest relevant transaction commit LSN whose changes have been durably applied to Delta.

Do not claim these are equivalent.

A table can have:

```text
latest_seen_lsn > last_processed_lsn
```

during processing or failure.

Do not use `latest_seen_lsn` as proof that Delta is synchronized.

# 32. Most important instruction

**Correctness takes priority over selective-reload optimization.**

The desired end state is:

```text
Normal operation:
    WAL → CDC → Delta

WAL pressure:
    inspect WAL → identify affected tables
    → establish safe boundary
    → reload affected tables
    → new CDC generation
    → resume

If selective recovery cannot be proven safe:
    → full reload all active tables
```

A working full-reload fallback is preferable to an unsafe selective-recovery implementation.

Do not declare success merely because the code runs.

The Phase 3 implementation must demonstrate, through controlled experiments, that the chosen recovery-boundary mechanism does not lose PostgreSQL changes during concurrent activity.

Start by inspecting the existing Phase 2 implementation and produce the code-specific implementation plan before making modifications.
