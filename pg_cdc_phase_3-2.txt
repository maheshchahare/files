# 3. Re-examine Stage 2's Sequence B boundary

Stage 2 established:

```text
new slot created
        ↓
full load
        ↓
CDC replay
```

is safe for the tested scenarios.

However, identify and test the additional boundary condition that Stage 2 did not independently establish:

```text
old-slot analysis
        ↓
new slot creation
```

This ordering can create a lost-change window.

Example:

```text
T0 old slot contains backlog

T1 analyze old slot
   affected tables = {A, B}

T2 UPDATE table C commits

T3 create new slot

T4 selectively reload A and B

T5 start CDC
```

The change to C can be absent from both:

* old-slot affected-table analysis
* new slot

and therefore be lost.

This is a critical correctness issue.

> The new slot must exist BEFORE the old-slot WAL analysis begins.

Explain precisely why this ordering prevents the analysis-to-new-slot gap.

Do not assume this is safe merely from theory.

# 7. Important semantic distinction

Do NOT describe the full load as:

> "full load from an LSN"

A PostgreSQL full load is a database snapshot/read operation.

The correct conceptual model is:

```text
Recovery boundary
        +
consistent PostgreSQL SELECT
        +
new-slot CDC stream
```

The implementation must establish why the combination covers every change exactly once or in an idempotently replayable manner.

# 10. Recovery manifest boundary semantics

Define exactly what it means for a table to be "affected."

A table is affected if the old-slot logical-decoding stream shows a committed transaction modifying that table within the discarded/recovery range.

Important:

* include all tables touched by a multi-table transaction;
* deduplicate repeated changes;
* do not treat BEGIN as evidence of a table change;
* do not treat COMMIT alone as evidence of a table change;
* preserve the transaction's membership correctly;
* do not lose table membership when parsing large transactions across batches;
* ensure uncommitted trailing transactions are not falsely included;
* ensure schema-qualified names are preserved.

If the parser cannot establish transaction membership safely, fail closed.

# 13. Old-slot retirement safety

Do NOT retire the old slot immediately after creating the new slot.

Define an explicit retirement gate.

Recommended minimum gate:

```text
new slot created successfully
AND
manifest persisted successfully
AND
all required selective reloads completed successfully
AND
new CDC cycle completed successfully
AND
new CDC watermark/state persisted successfully
AND
post-recovery validation passed
```

Only then may:

```text
old slot → retired
```

If any condition fails:

```text
old slot remains available
recovery remains resumable
```

Do not create a code path that drops the old slot merely because the new slot exists.

# 17. Failure handling

The system must fail closed when any of the following occurs:

* old slot disappears before analysis completes;
* WAL gap is detected;
* wal2json parsing becomes ambiguous;
* transaction membership cannot be established;
* affected-table analysis is incomplete;
* DDL is detected or cannot be ruled out when required;
* new slot creation fails;
* selective reload fails;
* CDC validation fails;
* generation identity is ambiguous;
* manifest state is corrupt;
* checkpoint/state is inconsistent.

In uncertain cases:

```text
RECOVERY_REQUIRED
```

must remain the safe outcome.

Never convert uncertainty into:

```text
NORMAL
```

# 18. DDL limitation

Stage 2 established that wal2json does not provide sufficient information through the current analyzer to safely identify an ALTER TABLE event during the discarded period.

Therefore:

> Selective recovery MUST NOT be used when schema-changing DDL may have occurred within the recovery interval, unless a separate reliable DDL detection mechanism is implemented.

Do not weaken this requirement.

Determine how the orchestrator will detect or establish the absence of DDL.

If it cannot establish this reliably, route to:

```text
full-reload-all
```

rather than selective recovery.
