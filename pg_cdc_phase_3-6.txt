# PHASE 3 — STAGE 7

## Root-Cause and Close Delta Convergence Gap

Stage 6 produced valuable crash-safety evidence but did NOT fully close E1–E4.

Current status:

```text
E1: ORCHESTRATION PASS / DATA CONVERGENCE UNRESOLVED
E2: ORCHESTRATION PASS / DATA CONVERGENCE UNRESOLVED
E3: ORCHESTRATION PASS / DATA CONVERGENCE UNRESOLVED
E4: ORCHESTRATION PASS / DATA CONVERGENCE UNRESOLVED

No-change cycle: PASS
Retirement gating: PASS
Production Ready: NO
SelectiveRecoveryEnabled: false
```

Stage 6 also fixed two real issues:

1. `get_recovery_generation()` and `get_recovery_manifest()` now call `_ensure_metadata_tables()`.
2. Resume from `RECOVERY_CDC_VALIDATING` now re-attempts the persisted watermark advance and treats an already-past slot position as an idempotent no-op.

The remaining blocker is:

> In all four E1–E4 tests, the PostgreSQL source contained the expected transaction changes and the CDC watermark advanced to that transaction's real COMMIT LSN, but the Delta verification still showed the pre-existing seed value.

Do NOT assume this is merely a test-harness problem.

The objective of Stage 7 is to determine exactly why this happened and prove whether the production CDC application path is safe.

---

# 1. ABSOLUTE RULE

Do NOT modify the crash tests merely so that they report PASS.

Do NOT weaken the convergence assertion.

Do NOT replace actual Delta verification with:

* function return values
* logs
* row counts alone
* expected values generated by the test
* LSN assertions
* "no exception was raised"

The acceptance condition is:

```text
PostgreSQL final state
        ==
Delta final state
```

for every source row affected by the tested transaction.

If Delta does not contain the expected state, the test remains FAIL/UNRESOLVED until the root cause is identified.

# 3. INVESTIGATE DEAD-LETTER / SILENT FAILURE

The Stage 6 result specifically suggested a possible silently handled apply failure.

Inspect all relevant code for:

```python
try:
    ...
except Exception:
    ...
```

and equivalent patterns.

Search especially for:

* dead-letter writes
* per-row exception handling
* schema evolution handling
* Fivetran-column dependencies
* missing-column handling
* unsupported data types
* malformed WAL rows
* MERGE exceptions
* DELETE exceptions
* ignored return values
* warnings that do not fail the batch

Determine whether this can happen:

```text
source transaction
      ↓
apply function
      ↓
row rejected/skipped
      ↓
dead letter
      ↓
function still returns success
      ↓
watermark persisted
```

If that sequence is possible, it is a serious correctness bug.

Fix it so that:

```text
any unapplied required WAL effect
        =>
CDC cycle FAILS
        =>
watermark NOT advanced
```

Do not silently convert data loss into a successful CDC cycle.

# 11. CRITICAL WATERMARK TEST

This stage must determine whether the current implementation could ever execute:

```text
Delta APPLY FAILED
        ↓
watermark persistence SUCCESS
```

If yes, this is a correctness bug.

The required behavior is:

```text
Delta APPLY FAILED
        ↓
CDC cycle FAILS
        ↓
NO app_confirmed_lsn advancement
        ↓
NO slot advance
        ↓
transaction remains recoverable
```

Add a focused test for this.

Inject an actual apply failure after WAL has been read but before successful completion.

Verify:

```text

slot confirmed_flush_lsn unchanged

```

This test is extremely important.

Do not optimize for getting:


Optimize for discovering whether this invariant is genuinely true:

> **No source transaction may be considered durably processed until its required effects are actually present in Delta, and no source transaction may become permanently unrecoverable through watermark/slot advancement before that condition is true.**

If the current architecture cannot guarantee that property, identify the exact architectural limitation rather than hiding it behind test-fixture changes.
