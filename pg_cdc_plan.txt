Our intended ordering is:

1. Read/peek WAL batch.
2. Apply Delta MERGE operations successfully.
3. Determine the application watermark.
4. Persist the application checkpoint.
5. Advance/acknowledge the PostgreSQL logical replication slot.

* Before processing: app checkpoint = 100, slot confirmed_flush_lsn = 100.
* CDC changes through LSN 120 are successfully applied to Delta.
* Application checkpoint is durably updated to 120.
* Process crashes BEFORE slot advancement.

After restart it is valid for:

* app_confirmed_lsn = 120
* confirmed_flush_lsn = 100

This is SAFE because the slot is simply behind the application checkpoint. Re-reading 100→120 should be safe because Delta MERGE/application processing must be idempotent.

**Do not use equality as the invariant.**

* `confirmed_flush_lsn < app_confirmed_lsn`

* `confirmed_flush_lsn == app_confirmed_lsn`
  → normal synchronized state.

* `confirmed_flush_lsn > app_confirmed_lsn`
  → UNSAFE.
  → The slot has advanced beyond what the application has durably recorded.

`WAL_GAP_DETECTED → RECOVERY_REQUIRED`

## 8. Recovery strategy

The revised plan must distinguish between two situations.

### Situation 1 — WAL still available

If the application checkpoint is behind the slot but the required WAL is still available:

* do not resync unnecessarily.

If:

`app_confirmed_lsn < restart_lsn`

then exact CDC continuation from that slot is impossible.

If we have NO independent durable change-history mechanism:
