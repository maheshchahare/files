# 3. The central question for Stage 2

We need to validate whether this recovery strategy is actually safe:

```text
OLD SLOT
   │
   │ WAL backlog
   ▼
PEEK / ANALYZE
   │
   ▼
identify affected tables
   │
   ▼
establish recovery boundary
   │
   ▼
NEW CDC GENERATION
   │
   ▼
full load affected tables
   │
   ▼
new CDC resumes
```

The key correctness question is:

> Can a PostgreSQL change occur during the transition between WAL analysis, recovery-boundary establishment, selective full load, and new CDC startup without being lost or permanently duplicated?

Do not assume the answer is yes.

Prove it experimentally.

# 6. Experiment A — Change after affected-table analysis

Test this exact scenario:

```text
1. Old slot has backlog.
2. Analyze old slot using PEEK.
3. Identify table A as affected.
4. Before full load starts:
       UPDATE table_A
5. Continue recovery.
6. Full load table_A.
7. Start/use new CDC generation.
8. Verify final Databricks/test-target state.
```

The purpose is to determine:

> Is the change occurring after analysis but before full load guaranteed to be captured by the new CDC generation without being lost?

Record:

```text
old slot
analysis start LSN
analysis end/boundary LSN
new slot creation LSN
full-load snapshot/boundary
change commit LSN
new CDC starting point
final table state
```

Expected outcome must be explicitly defined.

If the proposed architecture cannot guarantee correctness, mark the design unsafe and redesign the ordering.

# 15. Determine whether Sequence B is actually safe

The current reasoning says:

```text
Analyze old slot
       ↓
Create new slot
       ↓
Full load
       ↓
CDC
```

and assumes:

> New slot creation establishes a boundary such that post-creation changes cannot be missed.

This must now be experimentally validated.

Specifically answer:

1. What exact LSN does the new slot represent?
2. What does `restart_lsn` mean immediately after creation?
3. What does `confirmed_flush_lsn` mean immediately after creation?
4. If a change occurs immediately after slot creation, is it guaranteed to be decoded by the new slot?
5. If a full load reads data after that change, can CDC later safely replay it?
6. If CDC replays it, is the resulting operation idempotent?
7. If the full load happens after the change but CDC also contains the change, can this cause a final-state problem?
8. If yes, does the current Delta MERGE design tolerate it?
9. If not, what ordering or snapshot mechanism is required?

Do not answer these from assumption alone.

Use:

* controlled experiments;
* PostgreSQL documentation where applicable;
* actual LSN observations.

---

# 16. Test final-state correctness, not only CDC visibility

A change being present in the new slot is not sufficient.

Example:

```text
UPDATE A → value = 20

full load sees value = 20

CDC later replays UPDATE
```

This may be harmless.

But another ordering could be:

```text
UPDATE A → value = 20

CDC applies UPDATE 20

full load then overwrites with older snapshot value = 10
```

which would be incorrect.

Therefore every experiment must verify:

```text
Final PostgreSQL state
        ==
Final recovered Delta/test-target state
```

not merely:

```text
CDC contained the event
```
