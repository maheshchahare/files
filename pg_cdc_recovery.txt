I am building a custom PostgreSQL → Databricks CDC pipeline using PostgreSQL logical replication + wal2json, without Debezium/Kafka.

IMPORTANT: Before modifying any code, inspect the existing codebase and understand the current CDC flow, checkpoint handling, replication slot handling, and error/recovery logic.

I have identified a critical correctness issue:

The current implementation appears to read from PostgreSQL's current `restart_lsn` as the starting point. This is unsafe.

Example:

- Our durable application checkpoint = LSN 100
- Pipeline is down
- PostgreSQL WAL advances
- The replication slot's restart_lsn advances to LSN 200
- WAL between 100 and 200 is no longer available
- On restart, if the application simply starts reading from restart_lsn=200, changes 100→200 are silently skipped.

This MUST NOT happen.

The application must distinguish:

1. NORMAL RECOVERY:
   application_checkpoint >=? appropriate available WAL boundary and the required WAL is still available.
   Resume from the application's durable CDC checkpoint.

2. WAL GAP / DATA-LOSS RISK:
   application_checkpoint is older than the WAL that is still available from the replication slot.
   The application must NOT silently jump to restart_lsn.
   It must detect the gap, stop normal CDC processing, mark the pipeline as OUT_OF_SYNC / RECOVERY_REQUIRED, and invoke the recovery/resync workflow.

3. FIRST RUN:
   There is no application checkpoint yet.
   This must be handled separately from a WAL-gap condition.

4. SLOT RESET / RECREATION:
   If the replication slot has been recreated, advanced, invalidated, or otherwise changed, this must not be treated as normal continuation without validation.
